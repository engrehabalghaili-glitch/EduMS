# الدليل الهندسي لإدارة النماذج والبيانات (Frontend DTOs & Interfaces Guidelines)

يُعتبر التعامل مع البيانات الواردة من الباك إند (API Contracts) وترجمتها إلى واجهات أمامية (Interfaces) من أهم ركائز استقرار المشاريع الضخمة (Enterprise Projects). 

تم إعداد هذا التقرير لتوثيق **أفضل الممارسات (Best Practices)** التي تم التوصل إليها لتنظيم الـ Interfaces الخاصة بالـ DTOs (Data Transfer Objects) في مشروع إدارة المدارس.

---

## 1. التحدي: تفكير الباك إند مقابل تفكير الواجهات الأمامية
في الباك إند، يتم تصميم الـ DTOs بناءً على **جداول قاعدة البيانات (Tables)**. أما في الواجهات الأمامية، فنحن نصمم النظام بناءً على **الشاشات والعمليات (Workflows/Screens)**. 
بناءً على هذا الاختلاف، فإن التحدي الأكبر هو: *أين نضع الـ Interfaces في الفرونت إند بحيث لا يتشتت الكود ولا تنكسر الشاشات إذا تغيرت جداول الباك إند؟*

---

## 2. المعمارية المعتمدة: "النهج الهجين" (The Hybrid Approach)

للحصول على أفضل نتيجة تجمع بين التنظيم الصارم وسرعة التطوير، تم اعتماد **النهج الهجين** والذي يتكون من شقين:

### الشق الأول: المكتبة المركزية للباك إند (Single Source of Truth)
يتم إنشاء مجلد مركزي في قسم الـ `core` ليحتوي على جميع الـ Interfaces التي تطابق جداول الباك إند **حرفياً**. هذا المجلد يمثل "عقد الاتصال" (API Contract).

**هيكلية المكتبة المركزية:**
يتم تقسيم الـ Interfaces داخل المكتبة المركزية بناءً على الأقسام الرئيسية (Domains) وليس بشكل فوضوي.

```text
src/
└── app/
    ├── core/
    │   └── api/
    │       └── models/                <-- (المكتبة المركزية)
    │           │
    │           ├── student-affairs/   <-- (نماذج شؤون الطلاب)
    │           │   ├── student.dto.ts
    │           │   ├── parent.dto.ts
    │           │   └── index.ts       
    │           │
    │           ├── financial/         <-- (نماذج المالية)
    │           │   ├── invoice.dto.ts
    │           │   └── index.ts
    │           │
    │           └── shared/            <-- (نماذج عامة مشتركة)
    │               ├── user.dto.ts
    │               └── index.ts
```

> [!TIP]
> تجميع الـ DTOs في مجلد مركزي يسهل استخدام أدوات التوليد التلقائي (مثل Swagger Generator) مستقبلاً لتحديث هذا المجلد بضغطة زر دون المساس بباقي المشروع.

---

### الشق الثاني: حماية الشاشات باستخدام نماذج الواجهة (ViewModels)
القاعدة الذهبية هنا هي: **يُمنع استخدام الـ DTO المركزي مباشرة داخل ملفات العرض (HTML/UI) الخاصة بالشاشات.**

الـ DTO يحتوي فقط على بيانات قاعدة البيانات (مثل `birthDate` كـ نص)، لكن الشاشة قد تحتاج لخصائص إضافية لا تهم الباك إند (مثل `isSelected` أو `age`). 

**طريقة التطبيق (الوراثة):**
في مجلد الـ `data-access` الخاص بكل شاشة، نقوم بإنشاء نموذج واجهة (ViewModel) **يرث** الـ DTO المركزي ويضيف عليه متطلبات الشاشة:

```typescript
// 1. الاستيراد من المكتبة المركزية
import { StudentDto } from '@core/api/models/student-affairs';

// 2. إنشاء نموذج الشاشة المستقل
export interface StudentViewModel extends StudentDto {
  // حقول خاصة بالفرونت إند فقط (UI State)
  isSelected?: boolean;
  rowNumber?: number;
}
```

> [!IMPORTANT]
> هذا الفصل يضمن أنه إذا قام فريق الباك إند بتعديل `StudentDto`، فإن التعديل ينعكس في المكتبة المركزية فقط. الشاشة ستستمر بالعمل عبر `StudentViewModel` مع إجراء تعديلات طفيفة في خدمة الـ Mapping.

---

## 3. تحسين استيراد الملفات: استخدام الفهرسة (Barrel Files - index.ts)

لمنع تراكم أسطر الاستيراد (Imports) في ملفات المشروع، يتم استخدام تقنية الـ **Barrel Files**.
في كل مجلد فرعي داخل المكتبة المركزية، يتم إنشاء ملف `index.ts` يعمل كـ "موظف استقبال" أو "فهرس".

**محتوى ملف `index.ts`:**
يقوم بجمع كل الملفات الموجودة في مجلده وتصديرها:
```typescript
export * from './student.dto';
export * from './parent.dto';
```

**النتيجة السحرية عند الاستيراد في الشاشات:**
بدلاً من كتابة مسارات طويلة ومزعجة لكل ملف بشكل منفصل:
```typescript
import { StudentDto } from '@core/api/models/student-affairs/student.dto';
import { ParentDto } from '@core/api/models/student-affairs/parent.dto';
```
يكتفي المطور بكتابة سطر واحد أنيق ومختصر:
```typescript
import { StudentDto, ParentDto } from '@core/api/models/student-affairs';
```

---

## 4. الخلاصة والتوصيات

باتباع هذا الدليل، يضمن فريق تطوير الواجهات الأمامية تحقيق الفوائد التالية:
1. **أكواد خالية من التكرار (DRY):** كل جدول له DTO واحد فقط في المكتبة المركزية.
2. **قابلية صيانة عالية (Maintainability):** الشاشات محمية بنماذج `ViewModels` خاصة بها.
3. **أكواد نظيفة وقصيرة:** بفضل استخدام ملفات `index.ts`.
4. **عمارة قابلة للتوسع:** جاهزة للعمل مع فرق متعددة وأنظمة API ضخمة بمرونة تامة.
